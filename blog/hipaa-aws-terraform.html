Building HIPAA-Compliant Infrastructure on AWS with Terraform

👨‍⚕️
Muhammad Raees
May 2026 · 9 min read
Cloud Security · AWS · Terraform

Healthcare organizations moving to the cloud face a challenge that most cloud engineers underestimate: HIPAA compliance is not a checkbox, it is an architecture decision. Every layer of your AWS infrastructure — from VPC design to S3 bucket policies to CloudTrail configuration — must be built with Protected Health Information (PHI) in mind. In this article I walk through how I provision HIPAA-aligned AWS environments using Terraform, covering the five most critical controls.

Why HIPAA Compliance Matters in Infrastructure

HIPAA's Security Rule requires covered entities to implement technical safeguards protecting electronic PHI (ePHI). As an infrastructure engineer with a clinical pharmacy background, I've seen firsthand what happens when these safeguards fail — audit failures, breach notifications, and loss of patient trust. Terraform lets us encode these requirements as code, making them repeatable, auditable, and version-controlled.

Key principle: HIPAA doesn't mandate specific technologies — it mandates outcomes: confidentiality, integrity, and availability of ePHI. Your Terraform code is how you prove you've achieved those outcomes.

1. VPC Design — Network Segmentation

The foundation is a properly segmented VPC. Clinical data workloads must run in private subnets with no direct internet access. Only a hardened bastion or VPN gateway sits in the public subnet.

# terraform/modules/vpc/main.tf
resource "aws_vpc" "hipaa_vpc" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true
  enable_dns_support   = true
  tags = { Name = "hipaa-vpc", Environment = "production" }
}

resource "aws_subnet" "private" {
  vpc_id                  = aws_vpc.hipaa_vpc.id
  cidr_block              = "10.0.1.0/24"
  map_public_ip_on_launch = false  # never true for PHI workloads
}

2. Encryption at Rest and in Transit

Every storage layer must encrypt PHI. For S3 this means server-side encryption with KMS customer-managed keys (CMKs). For RDS this means enabling storage encryption. For EBS volumes attached to EC2 instances, encryption must be enforced at the account level.

resource "aws_s3_bucket_server_side_encryption_configuration" "phi" {
  bucket = aws_s3_bucket.phi_data.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm     = "aws:kms"
      kms_master_key_id = aws_kms_key.phi_key.arn
    }
    bucket_key_enabled = true
  }
}

resource "aws_s3_bucket_public_access_block" "phi" {
  bucket                  = aws_s3_bucket.phi_data.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

3. IAM Least-Privilege

HIPAA's minimum necessary standard maps directly to IAM least-privilege. No role should have * actions on PHI resources. Each service gets a purpose-specific role with explicit, narrow permissions — and all permissions are defined in Terraform, never clicked in the console.

resource "aws_iam_policy" "phi_read_only" {
  name = "PHIReadOnlyAccess"
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect   = "Allow"
      Action   = ["s3:GetObject", "s3:ListBucket"]
      Resource = [aws_s3_bucket.phi_data.arn, "${aws_s3_bucket.phi_data.arn}/*"]
      Condition = {
        Bool = { "aws:SecureTransport" = "true" }
      }
    }]
  })
}

4. CloudTrail — Audit Logging

HIPAA requires audit controls — logs of who accessed what PHI and when. CloudTrail must be enabled in all regions, with logs sent to an S3 bucket in a separate, locked-down account. Log integrity validation must be turned on.

resource "aws_cloudtrail" "hipaa_trail" {
  name                          = "hipaa-audit-trail"
  s3_bucket_name                = aws_s3_bucket.audit_logs.id
  include_global_service_events = true
  is_multi_region_trail         = true
  enable_log_file_validation    = true  # tamper detection
  kms_key_id                    = aws_kms_key.trail_key.arn
}

5. AWS Config — Continuous Compliance Monitoring

Terraform provisions the initial state, but drift happens. AWS Config continuously evaluates your resources against HIPAA-aligned managed rules — alerting you when a misconfiguration occurs.

  • s3-bucket-public-read-prohibited — catches any bucket that becomes public
  • encrypted-volumes — flags unencrypted EBS volumes
  • cloudtrail-enabled — verifies logging is always on
  • iam-root-access-key-check — ensures root account has no active keys
  • rds-storage-encrypted — enforces database encryption

Putting It All Together

The real power of this approach is that your compliance posture is code — it lives in version control, it gets reviewed in pull requests, and it can be audited by your compliance team without screenshots or manual checks. When HIPAA auditors ask for evidence of your technical safeguards, you hand them a Terraform repository and a CloudTrail log.

As a pharmacist turned cloud engineer, I've sat on both sides of this: the clinical side where a PHI breach means real harm to real patients, and the engineering side where the right architecture prevents it. These aren't separate concerns — they are the same concern, expressed in different languages.

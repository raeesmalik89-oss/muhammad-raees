Monitoring Clinical Systems with Prometheus & Grafana

Muhammad Raees

Observability · Prometheus · Grafana

Most Prometheus and Grafana tutorials show you how to monitor CPU and memory. That's fine for a web app. But when you're monitoring a pharmacy management system, an EHR, or a clinical decision support API, the metrics that matter are fundamentally different. In this article I'll show you how I set up observability for healthcare microservices — including the custom metrics, alert rules, and dashboard design choices that actually serve clinical operations teams.

The Problem with Generic Monitoring in Healthcare

Generic infrastructure monitoring tells you when a server is unhealthy. Clinical monitoring tells you when a patient-facing service is degrading. These are different things. A pharmacy dispensing API running at 100% CPU might still be serving requests fine. But if its p99 response time crosses 3 seconds, a pharmacist is waiting — and that delay has downstream patient safety implications.

The shift from infrastructure monitoring to clinical service monitoring requires defining clinically meaningful SLOs (Service Level Objectives) and building alerts around them.

Key insight from pharmacy practice: Alert fatigue is as dangerous in IT as it is in clinical settings. When every alert is critical, none are. Design your Prometheus alert rules with the same discipline a pharmacist uses to triage incoming orders — not everything needs immediate action.

Custom Metrics for Clinical Services

Beyond the default node_exporter metrics, healthcare services need custom application metrics exposed via the Prometheus Python client:

from prometheus_client import Counter, Histogram, Gauge

# Track prescription API requests by outcome
prescription_requests = Counter(
    'pharmacy_prescription_requests_total',
    'Total prescription API requests',
    ['method', 'status', 'drug_class']
)

# Track dispensing decision latency — clinical SLO: p99 < 2s
dispensing_latency = Histogram(
    'pharmacy_dispensing_decision_seconds',
    'Time to return dispensing decision',
    buckets=[0.1, 0.5, 1.0, 2.0, 5.0]
)

# Track active drug interaction checks in flight
active_interaction_checks = Gauge(
    'pharmacy_active_interaction_checks',
    'Concurrent drug interaction checks in progress'
)

Alert Rules That Matter

The four alerts I configure for every clinical service deployment — mapped to real patient impact:

🔴 Dispensing API Down

Service unavailable for >60s. Immediate page. Pharmacists cannot process prescriptions.

🔴 Interaction Check Latency

p99 > 3s for 5 min. Clinical workflow blocked. Pharmacists waiting on safety check results.

🟡 Error Rate Elevated

5xx rate > 2% for 10 min. Service degraded. Some requests failing silently.

🟡 Queue Depth Rising

Pending prescription queue > 50 for 5 min. Capacity issue forming before it becomes critical.

# prometheus/rules/clinical-alerts.yaml
groups:
  - name: clinical.rules
    rules:
      - alert: DispensingAPIDown
        expr: up{job="pharmacy-api"} == 0
        for: 1m
        labels:
          severity: critical
          clinical_impact: high
        annotations:
          summary: "Pharmacy dispensing API is unreachable"
          runbook: "https://wiki.internal/runbooks/pharmacy-api-down"

      - alert: HighDispensingLatency
        expr: |
          histogram_quantile(0.99,
            rate(pharmacy_dispensing_decision_seconds_bucket[5m])
          ) > 3
        for: 5m
        labels:
          severity: warning

Grafana Dashboard Design for Clinical Teams

Standard Grafana dashboards are built for engineers. Clinical operations dashboards need to be readable by people who don't know what p99 means. My dashboard design principles for healthcare:

  • Top row: traffic light status — green/amber/red stat panels for each critical service. Readable at a glance from across the room
  • Second row: patient-facing SLOs — "Dispensing decisions in <2s: 99.4%" rather than raw latency histograms
  • Third row: volume and trends — prescriptions processed per hour, error counts, queue depths with time annotations for shift changes
  • Bottom row: infrastructure — for engineers, not clinicians. CPU, memory, pod restarts
  • Annotations — mark deployments and configuration changes so teams can correlate changes with metric shifts instantly

Reducing Alert Fatigue — The Clinical Lesson Applied to IT

In clinical pharmacy, one of the biggest patient safety challenges is alert fatigue: when drug interaction warnings fire so frequently that pharmacists start clicking through them without reading. The same problem exists in IT monitoring — when every threshold breach generates a page, on-call engineers start ignoring alerts.

The fix in both domains is the same: alert on patient/user impact, not on technical thresholds. A server at 85% CPU is not an alert. A service failing to return dispensing decisions is. Design your Prometheus rules around the clinical outcome you're protecting, and your on-call team will actually trust the alerts they receive.
